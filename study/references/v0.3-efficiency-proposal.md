# v0.3 — efficiency proposal

**Status: proposed — unratified. Not a live spec.** Nothing here has been run. v0.2 is what
executes today; this is the next thing to test, and it should be tested *after* v0.2 has produced
at least one run, so the two changes do not confound each other.

Every number below marked *(hypothesis)* is a prediction, not a measurement. v0.1's numbers are
measurements.

## Where v0.1 actually spent its budget

| Stage | Tokens | Tool calls | Wall time |
|---|---|---|---|
| harvest ×4 | 440,703 | 154 | ~7m (parallel) |
| audit ×1 | 197,304 | 75 | **19m 28s** |
| orchestrator | 875,870 → 1,303,130 | — | whole session |

Two separate problems, and they need different fixes:

- **Cost** is dominated by the orchestrator. v0.2 addresses this by moving merge-and-tier out to a
  dispatched agent and by mandating a fresh session.
- **Latency** is dominated by the audit — 19.5 minutes, nearly three times the entire parallel
  harvest, almost all of it spent re-fetching 51 URLs the harvest had already opened.

v0.2 does not touch latency at all. That is what v0.3 is for.

---

## Change 1 — Store the evidence instead of re-fetching it

**The proposal.** Add a required `quote` field: the verbatim sentence from the source that
supports the claim, ≤300 characters. The harvester already has the page open when it writes the
row, so capturing it is free. The audit then verifies **quote against claim** by reading, and
re-fetches only where the quote is missing, thin, or suspicious.

**Why this is a strengthening, not a weakening.** DFN-10 says an agent must state what it sees in
the same turn it names the source. Today that statement is transient — it exists in the agent's
return prose and is gone. A `quote` field makes it a stored, checkable artifact. The row stops
asserting *"this source supports me"* and starts showing the sentence that does.

It also targets v0.1's most common defect directly. Twelve of thirteen changed rows were
`wounded`, and five shared one signature: a real rule quoted correctly with a plausible rationale
attached that the source never states. A stored quote makes that visible on the row itself —
the rationale is simply not in the quoted text — without anyone opening a page.

**Effect** *(hypothesis)*: audit network fetches drop from 51 to roughly 10; audit wall time from
19.5m to ~6m; audit tokens from 197k to ~80k. Harvest grows by roughly 40 tokens per row, call it
2k per run. Net strongly positive, because a fetch costs far more than a stored sentence.

**The risk, stated plainly.** This trusts the harvester's transcription. A fabricated quote
defeats the whole scheme, and it would be *harder* to catch than a fabricated URL because it looks
like evidence. Mitigation: the verify stage re-fetches a stratified sample — every `exercise` row,
every row containing a number, every templated or unpinned-looking URL, plus a random remainder —
and **logs exactly what it sampled and what it did not**. A silent sample would read as full
coverage, which is worse than no sampling.

## Change 2 — Split the audit by what it actually needs

The audit does two jobs with different requirements:

- **Verify** — mechanical: does this quote support this claim, is this URL live. Needs one row at
  a time, not the full set. Can start the moment the first harvest file lands.
- **Absence** — judgment: what is missing. Needs the complete row set, and needs a strong model
  writing its own must-know list before reading anything.

Splitting them means verify starts during harvest instead of after merge, and can run on a cheaper
tier. Absence stays where it is, on the strongest model available, unchanged — the retro was clear
that this brief produced the run's single best finding and should not be economized.

**Effect** *(hypothesis)*: removes the verify pass from the critical path entirely. End-to-end wall
time from ~30m to ~12m.

## Change 3 — Model assignment as a declared variable

v0.1 ran Sonnet harvest → Opus audit and recorded it as MSR-5. v0.3 should declare it per stage
and make it visible in the telemetry:

| Stage | Proposed | Why |
|---|---|---|
| harvest | Sonnet | quality held; this is volume search work |
| merge and tier | Sonnet | bounded, mechanical, returns ≤300 words |
| verify | Haiku | comparing a stored quote to a claim is a small judgment |
| absence | strongest available | the one stage where reasoning quality clearly paid |

The corpus has twice found that a well-specified reading position beat a bigger allocation. Verify
is the cheapest test of that claim yet available: if Haiku catches the same quote/claim mismatches
Opus did, that is a real result about where model tier matters.

## Change 4 — Never render with the model

v0.1 did this correctly by accident and never wrote it down. The guide is 164KB of HTML. Emitting
it as model output would have cost roughly 40k output tokens; generating it with a script cost
zero. **The renderer is code, and processing must never be a stage that asks a model to produce
the document.** The model authors the self-check questions and the honest-limits prose — a few
hundred tokens — and the script does the rest.

This belongs in v0.2's SKILL.md as a rule, not deferred to v0.3, and it is written there.

## Change 5 — The time-budget question

Unresolved, and worth settling before v0.3 rather than during it.

v0.1's guide reported a *minimum viable pass* of 188 and 167 minutes for a reader who had about
60. The triage line was honest; the definition ("all fundamentals plus all traps") was simply not
minimal for a topic of that size.

**The argument for accepting a time budget as an input:** it is not a use case. A use case says
*what you need the knowledge for* and would bias what gets researched — which is exactly what the
consumer-agnostic design exists to prevent. A time budget says only *how much you can consume*,
which is a property of the reader, not of the topic.

**The argument against:** it would still change what the analysis returns, and any input that
changes the rows makes them less reusable by a second consumer. A row set produced under a
60-minute budget is not the same artifact as one produced without.

**The resolution this proposes:** put the budget on the **consumer, never the analysis.** The
analysis keeps harvesting to its row budget with no knowledge of any reader. The `study` skill
gains an optional `--minutes N` that filters and orders the existing rows at render time. This
costs zero agents on a re-render, which is precisely the payoff the analysis/processing split was
built for and which v0.1 never got to demonstrate.

## What would confirm or kill this

Run the same single topic under v0.2 and then under v0.3, and compare:

1. **Tokens and wall time per stage.** The predictions above are falsifiable at that granularity.
2. **Defect catch rate — the one that matters.** v0.1's audit found 1 kill, 12 wounds, 2 depth
   corrections, 5 absence findings, and one row citing a 404 while claiming it had been opened.
   If v0.3's cheaper audit misses the 404 or the wounds, the saving is not a saving. **A cheaper
   run that catches less is a worse run, and this comparison is the only thing that distinguishes
   the two.**
3. **Whether any fabricated quote appears.** If the stratified sample ever catches a quote that is
   not in its source, Change 1 is unsafe as written and needs full verification back.

If Change 1 fails on point 3, the rest of the proposal still stands on its own — Changes 2, 3, and
4 are independent of it.
