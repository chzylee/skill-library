## 1. Problem Statement

You search to learn about something and you get links. You read them, you lose them, and
next time you start over. The knowledge never accumulates and nothing you learned last
month helps you this month.

`/study` should replace that: search a topic, get back something you can actually study
from, and keep it. Over time the kept things become a library, and because the library is
structured data rather than documents, it stays queryable across every topic you have
ever run.

The v0 prototype proved the pipeline works and produced 238 real rows across three runs.
It failed on presentation. The verdict on its output was *"all of these came out pretty
poorly done,"* refined during this session to: **"40 unorganized rows is a defect... facts
aren't a problem inherently. Disorganization and poor UX is."**

That distinction is the whole design. The content was never the problem. The organization
was.

---

## 2. What Makes This Cool

**The tool never has the final word.** Every path a reader takes ends at a firsthand
source. The tool finds, orders, and describes faithfully; the learning happens in the
source. That is the opposite of asking an AI to explain something to you, and it is what
makes the output trustworthy without requiring you to trust the tool.

Stated as the governing principle, in the author's words: **no claim should be made
without a traceable cause.**

**A textbook you can't get any other way.** Not authored prose. A reading path through
primary sources, chaptered by the ideas that actually bind them, ordered so each chapter
assumes the one before it.

**It compounds.** Run 40 topics over two years and you have a personal reference library
that is searchable across every topic at once, where every claim is one click from the
page it came from.

### The experience

**Browsing.** One page. A visual browser of every topic you have studied, sorted
alphabetically, taggable by hand, and filterable on three facets:

| Facet | Status today |
|---|---|
| run date | Already computed per run. |
| trust | `build_index.py` computes `unver`, a raw **count** of `asserted` rows. The facet needs a share, so this is `unver / len(live)`: one line of new arithmetic, not a new field. |
| `reference_class` | **Not available yet.** Decided at scope every run and then discarded, because it is not a stored field. Storing it is what turns it into a facet. See section 6. |

Mundane on purpose: when you are finding something you already know you want,
predictability beats design.

**Reading a topic.** A contents view. The topic broken into chapters in reading order,
each named for the idea that holds it together, each with one line on what it covers. You
see the shape of the whole topic without scrolling.

**Going deeper.** Open a chapter and get its items in order, one line each. Click an item
and it expands in place: the summary, what kind of thing it is, when it matters, and the
link out. Click the link and you leave for the source.

**Across topics.** Search from the same page over everything you have ever studied. A hit
opens that item, expanded, inside its chapter.

**The rule underneath it.** Traceable does not mean visible by default. It means reachable
in a known number of clicks. Every warrant, every merge log, every `none, because` exists
and is one expansion away. None of them clutter the page.

## 3. The Two Failure Modes This Design Guards Against

The author's own framing, and the organizing test for every decision below. Correctness
failures are already guarded by transparency: if a claim is wrong the source is right
there. What transparency does **not** guard is these two.

### Failure mode 1: poor UX

| Guard | Mechanized? | What it does |
|---|---|---|
| Chaptering exists and is non-degenerate | **Gate, script** | Build fails if any live row has no `chapter`; if any chapter has an empty `principle` or a `because` under 80 characters; or if `because` is mostly the concatenated subjects of its own members (token-overlap over 60%). |
| Chapters are the right size | **Gate, script** | Build fails if any chapter holds more than 12 members or if a topic with 15+ live rows produces fewer than 3 chapters. Without this, one broad chapter passes every text check and still violates success criterion 3. |
| No alphabetical ordering inside a topic | Architecture | Order comes from `chapter.members`. No code path sorts by subject. Not a gate; a rewrite could reintroduce one silently. |
| A contents view always exists | Architecture | Rendered from `chapter` records, which the gates above guarantee exist. |
| Progressive disclosure | Architecture | Summary by default, detail on click, source at the bottom. **No test would catch a regression here.** |
| Never render with the model | Architecture | There is no model path to HTML. **Also untested; a future stage could reintroduce one.** |
| Chapters name a real principle | **Neither. Needs a reader** | Whether `because` names a genuine binding idea rather than a fluent restatement is a judgment call no script can settle. This is the design's load-bearing risk, validated by independent read in section 11. |
| Chapters bound by principle, not surface | **Neither. Needs a reader** | See [the Chi finding](#research-that-shaped-this). Same judgment as the row above. |

**The honest split:** two real build gates, four architectural properties that no test
currently protects, and two judgments that cannot be automated at all. A script can prove a
chapter structure *exists*, is *non-degenerate*, and is *reasonably sized*. Only a reader can
say whether it is *good*. Calling the middle four "guards" would overstate them, which is why
they are labeled architecture instead.

### Failure mode 2: runaway token cost

Cost dials alone do not cover this, and assuming they do is the trap. In the v0.1 run the
**orchestrator was 58% of total cost, more than every sub-agent combined**, driven by
conversation length: 11.9M cache reads across 90 turns. None of that is on a dial.

*Source for both figures:*
`~/.claude/study/runs/kafka-api-contract-governance-2026-08-06/orchestrator-telemetry.md`,
section "Cost". The same file states two caveats that belong with the number: that
orchestrator was carrying a long design conversation before the run, and that the figure
should not be read as steady-state cost for the skill.

| Guard | Mechanized? | What it does |
|---|---|---|
| Run in a fresh session | No, a rule | The single largest lever available, and it is free. |
| Never render with the model | Yes, structural | The page is built by script; there is no model path to HTML. |
| Keep work off the orchestrator | Yes, structural | Every stage is a dispatched agent reading and writing files by path. |
| Cost shown before the run | Yes, script | The scope interview prints an estimate from prior per-stage token figures before dispatch. |
| Bounded agent count in the spec | Yes, script | Stage count and retry ceiling are read from the spec, not the operator's judgment. |
| Dials | Yes, input | Coverage, synthesis, trust. Presets by default. |
| Per-stage token reporting | Yes, script | Every run writes measured tokens per stage, so a preset that is nominally cheap and actually expensive is visible. |

**The counterintuitive part, and it comes from the author's own corpus.** The Analysis
Patterns page records a finding replicated across three domains: *distributed generation
does not beat solo generation, but independent challenge and audit passes do. Distribution
buys independence of challenge, not breadth of generation.* So turning the coverage dial
up should mean **more sources per agent and more search rounds**, not more agents. Money
spent on more parallel harvesting is the spend that does not pay.

## 4. Constraints

1. **Consumer-agnostic analysis.** The search does not know who is reading or why. The
   scope interview may ask *how much work to do* and *what the topic is*. It may never ask
   *what you want the knowledge for.*
2. **No claim without a traceable cause.** Splits in two: claims about the world trace to
   a **source**; decisions by an agent trace to a **stated reason**.
3. **Firsthand sources.** Open every source you cite and report what it says in the same
   turn. Never attach a rationale the source does not state.
4. **Empty is legal.** `none, because <reason>` beats invention, everywhere.
5. **Ledger, not deletion.** Killed and merged rows stay with their reason.
6. **No priority, importance, or relevance field on a row.** Those are the consumer's to
   compute.
7. **Never render with the model.**
8. **The existing 238 rows must survive.** Non-negotiable; the library already normalizes
   across schema versions, so this is cheap.

---

## 5. Premises

1. The v0's content was acceptable. Its organization was not. **Confirmed by the author
   this session.**
2. A study artifact is a reading path into primary sources, not authored prose.
3. Depth classifies; it does not sequence. Sequence comes from stated structure.
4. Chapters must be bound by a governing principle, not a surface topic.
5. Grouping is required before output.
6. The library and the guide are one product, not two.
7. Variation in tier assignment is tolerable because transparency is the guard. The rows
   present information under a stated lens and the reader decides what to trust.

## 6. The Schema

Five record types. The v0 forced knowledge and practice into one shape; they are separated
here.

### `row` — one piece of knowledge

| Field | Purpose |
|---|---|
| `subject`, `description` | What it says. `description` is a faithful summary, not an explanation. |
| `origin`, `evidence`, `quote` | Where it came from. `evidence` is `re-opened` / `asserted` / `authored`. `quote` is the supporting sentence. |
| `kind` | `fact` · `concept` · `procedure` |
| `binding` | `always` · `edge` · `choice` · `internal` |
| `binding_warrant` | One sentence: why this level, citing the signal in the source. Generalizes v0.2's `depth_check`. |
| `chapter` | Which chapter it belongs to. |
| `supersedes` | The row this replaces, if any. **New.** Without it the library slowly fills with claims that were true once. |
| `id`, `run`, `topic`, `lineage`, `grade`, `populated_at`, `schema_version`, `time_estimate_min` | Bookkeeping, unchanged from v0.2. |

**Identity (decided, eng review section 1).** The topic is the durable thing in the library;
a run is a version of it. So:

- **`topic_id` is globally unique and stable across runs.** `kafka-consumer-groups`, not
  `kafka-consumer-groups-2026-08-06`. Re-running a topic does not create a second topic.
- **Row ids are unique within their topic**, not merely within their run.
- Per-reader state in slice 3 keys to `(topic_id, row_id)`, which is why this has to be
  settled before that slice rather than during it.

Namespacing by *run* was considered and rejected: it makes ids unique, but it also makes
every re-run a fresh namespace, so reading progress would reset each time rather than carry.
Topic-level identity is the only shape where progress survives a re-run.

*Context from the author: the Terraform topic appearing twice with hand-picked `T-` and `T3-`
prefixes was a deliberate A/B test during early development, not the normal pattern. It is
evidence that run-scoped ids collide, not evidence that double-running is routine.*

**Open, and deferred to slice 3:** when a re-run produces a row that corresponds to an
earlier one, what establishes that correspondence so `supersedes` can be set and progress can
carry? Matching by subject is the obvious approach and is not obviously correct. Nothing in
slice 1 depends on the answer.

### `chapter` — a group of rows bound by one idea

| Field | Purpose |
|---|---|
| `principle` | The idea that binds these rows. The chapter's name. |
| `because` | The warrant. Why these belong together. |
| `members` | Row IDs, in reading order. |
| `order` | Where this chapter sits in the topic. |

**The test for `because`, and this is the rubric the whole design rests on:**

> Does `because` name a mechanism, constraint, or shared cause that is **not fully visible
> in any single member row**?

A real principle is emergent. You cannot read it off any one of its members, which is why
grouping them is worth doing. A restatement is not emergent, and it will read as a summary
of the list.

| Verdict | Example |
|---|---|
| Principle | "All four follow from offsets being committed after processing rather than before, so every one of them is a consequence of the same ordering choice." |
| Restatement | "These rows all cover offset commits, auto-commit settings, and delivery guarantees." |
| Surface grouping | "Everything about consumers." |

**What the build gate can and cannot check.** It can check that a `because` exists, is over
a length floor, and does not consist mostly of its members' own subject strings. It cannot
check that the first example above is better than a fluent-sounding fake. That gap is the
reason for the validation in [Recommended Approach](#11-recommended-approach).

### `practicum` — a drill or a real exercise

Separate from `row` because it does a different job and carries different fields. It has no
`binding`, which is the reason the v0's single shared schema was awkward.

| Field | Purpose |
|---|---|
| `id`, `run`, `topic`, `lineage`, `grade`, `populated_at`, `schema_version` | Bookkeeping, same as `row`. |
| `form` | `exercise` (real, someone else built it, verified to exist) or `drill` (authored here). |
| `chapter` | Which chapter it practices. Practicum belongs to a chapter, not to the topic at large. |
| `exercises` | Row IDs this gives you reps on. The link back to what it is for. |
| `prompt` | What the learner is asked to do. |
| `origin`, `evidence` | For `exercise`: the URL, `re-opened`, confirmed to exist. For `drill`: `model inference` and `authored`. |
| `time_estimate_min` | Same meaning as on a row. |

**Pairing rule, from van Merriënboer's recurrent/nonrecurrent split:** `fact` and `procedure`
rows want drills that build automaticity through reps. `concept` rows want worked examples
and self-explanation prompts, not reps. A stage authoring practicum reads the `kind` of the
rows in `exercises` and picks accordingly.

### `run` — the scope record

Boundary, excluded-adjacent list, **reference class** (currently decided at scope and then
thrown away; storing it gives the library a real facet for free), the dial settings chosen,
and the declared coverage.

### `note` — the human's own

**Not built, and not specified beyond this line.** Reserved only so the store layout leaves
room: notes keyed to row IDs, in their own append-only file, needing no warrant because the
author is the authority for their own note. Nothing in the current slice reads or writes
them.

### Migrating the 238 existing rows

Constraint 8 says they must survive, which needs a definition or it is untestable.

**"Survive" means: every legacy row stays queryable and readable, in a clearly labeled
unchaptered view, with no re-processing.** Not: every legacy row is retrofitted into the new
structure.

| Field | Legacy path |
|---|---|
| `binding` | Mechanical remap from `depth`: `orientation`/`operation` → `always`, `judgment` → `choice`, `mechanism` → `internal`. No `edge` rows exist in legacy data, and that is correct rather than lossy: the tier did not exist when they were written. |
| `kind` | **No mechanical mapping exists.** Old `type` was `concept`/`trap`/`exercise`/`drill`, which does not decompose into fact/concept/procedure without re-reading the row. Legacy rows carry `kind: unclassified`. |
| `chapter` | Absent. Legacy rows have no chapters and are not given any. |
| `binding_warrant` | Absent for legacy rows. `depth_check` carries over where present. |

The library's existing `normalize()` already handles v0.1, v0.2, and v0.3 rows coexisting,
so this is one more branch in a function built for exactly this. Legacy topics render in a
flat list with a banner saying they predate chaptering.

**Two upgrade paths, and the cheap one is proven by this design's own validation.**

| Path | Cost | Gets you |
|---|---|---|
| **Restructure only.** Run the structure stage over a legacy run's rows. No new search. | One agent | Chapters, ordering, and `choice` promotion on existing rows. This is exactly what section 11's validation does, so it is demonstrated before it is relied on. |
| **Full re-run.** New harvest under the new briefs. | A whole run | Everything above, plus `kind`, `binding_warrant`, `edge` rows the old briefs never looked for, and fresh sources. |

Restructuring is the default for a legacy topic worth keeping. A full re-run is for a topic
that matters enough to want the tiers the old harvest could not produce, and that is what
`supersedes` is for.

### The two axes

Both are defined by failure, which is what makes them one model rather than two borrowed
ones. **KIND** asks what kind of failure being wrong produces. **BINDING** asks when that
failure surfaces.

| `kind` | Being wrong costs you | Signal in the source |
|---|---|---|
| `fact` | A wrong value, locally. Correct it and you are done. | A value, name, default, limit, or version. A single lookup settles it. |
| `concept` | Everything downstream is wrong. Correcting it changes how you read other rows. | An explanation or a relationship. The sentence says *is*, *means*, or *because*. |
| `procedure` | You cannot complete the task. | Ordered steps with an outcome. Imperative verbs. |

**Tiebreak for `kind`:** when a sentence is both a value and an explanation, ask whether
correcting it would change how you read *other rows*. If yes it is a `concept`, even if it
looks like a fact. "BACKWARD means consumers upgrade first" reads as a definition and is a
`concept`, because being wrong about it makes you wrong about every compatibility decision
downstream.

| `binding` | You need it | Signal in the source |
|---|---|---|
| `always` | Every time you touch the thing | Stated flatly and unconditionally; other sources assume it |
| `edge` | Only when a condition fires | The source hedges: "unless", "note that", "only when" |
| `choice` | When picking among alternatives | The source presents options without settling them, **or two sources answer differently** |
| `internal` | To predict undocumented behavior | The source explains *why the system behaves this way* rather than *what to do* |

**Tiebreak for `edge` versus `choice`,** because a sentence like "unless X, use Y" satisfies
both signals: ask whether the source **tells you what to do** once the condition holds. If
it does, there is a right answer that applies conditionally, and that is `edge`. If it
leaves the decision to you, or another source answers differently, that is `choice`. Put
plainly: `edge` is a conditional rule, `choice` is an unsettled question.

### The general rule for any collision, on either axis

Two named tiebreaks cannot cover every pair, and enumerating all nine would be a rulebook
nobody follows. The general rule dissolves the problem instead of adjudicating it:

> **A sentence carrying two signals is two rows.**

Take: *"Because Kafka commits offsets after processing rather than before, a crashed consumer
reprocesses on restart, unless you disable auto-commit and manage offsets per record."* That
reads as an `internal` and an `edge` at once because it **is** two claims wearing one
sentence. Split it: one `concept` at `internal` explaining why the behavior exists, one
`procedure` at `edge` giving the conditional action. Both cite the same source. The chapter
puts them back together.

Same on `kind`: *"set `enable.idempotence=true`, which prevents duplicate writes by tracking
sequence numbers per partition"* is a `procedure` and a `concept` in one breath. Two rows.

This costs nothing the design was not already paying. Rows are meant to be atomic and
reconnected by chapters, so splitting is the native move, and cramming was always the defect.
The two named tiebreaks above stay for the case where a single genuine claim sits on a
boundary and splitting it would produce a fragment.

**The rule that makes tiering checkable:** a tier is assigned from something visible in the
quoted text, never from a judgment about how advanced something is. A third party can open
the source and check the tier the same way they check the claim.

**Mapping from v0.2:** `orientation` + `operation` → `always` (merged: both fail
immediately, so they answer the binding question identically; what separated them was
ordering, which now lives in chapters). `judgment` → `choice`. `mechanism` → `internal`.
`edge` is new, and it is where the "40 config-trivia rows" complaint actually lives: the
v0 had no home for detail that rarely applies but is critical when it does, so it filed as
`operation` and landed next to what a consumer group is.

**Dropped:** `trap` as a type. The author did not want it and it was added anyway. **Keep
the failure-literature search that produced it** — postmortems and incident writeups are
the best available source of `choice` material.

## 7. The Process

| Stage | Who | Does |
|---|---|---|
| **0 · Scope** | you | Interview: topic, boundary, excluded-adjacent, reference class, coverage dial. Expected cost shown. Blocking. |
| **1 · Harvest** | 2 agents, parallel, blind | Canon sources and failure literature. Rows with `kind` and `always`/`edge`/`internal`. |
| **2 · Structure** | 1 agent | IDs, merge true duplicates, **promote `choice`**, build chapters, warrant them, order them, author practicum. Synthesis dial set here. |
| **3 · Audit** | 1 agent, independent | Absence first, then verification. Trust dial set here. |
| **4 · Commit** | script | Append rows, chapters, practicum. |
| **5 · Build** | script | Rebuild the library page. |

### Three things worth knowing about this shape

**`choice` cannot be assigned at harvest.** It is defined by sources disagreeing, and a
harvester reading one page at a time, blind to the other harvester, structurally cannot
observe a disagreement. Only stage 2 holds every row at once. This also explains a v0.1
defect: judgment rows came from harvesters that could not see what judgment is made of, so
five of them filled the gap with invented rationale.

**Only the coverage dial is decided blind.** Synthesis and trust are decided with rows in
hand. Trust in particular is a pure post-pass, so a cheap run can be upgraded later without
re-searching anything. That matters for a library you return to.

**Coverage is gated on kinds, not volume.** The v0's gate is a row budget, which is item
volume, which the author's own `MSR-12` says cannot catch a correlated blind spot. The gate
becomes tier composition: `always` present, `choice` searched or explicitly declined. This
makes a facts-only run a **declared setting** rather than an accidentally thin result.

## 8. The Display

**One app. The separately generated guide file goes away.**

Today `/study-read` builds a real library app — sidebar, reading pane, cross-run search
with filters — and then embeds a separately rendered static `guide.html` in an iframe. Two
rendering systems that share nothing. That seam is why expansions are awkward: inside the
frame there is a document, not an app. Library search cannot land inside an expanded row
and library filters cannot narrow the guide.

The library already loads every row of every run. It should draw them.

**Two corrections, because this is the largest piece of work in the plan and the first draft
undersold it.**

*The data is a projection, not the full rows.* `build_index.py`'s `normalize()` keeps a
search-index shape: `subject`, `type`, `description` truncated to 300 characters, `depth`,
`evidence`, `grade`, and timing. It drops `origin` and would drop `quote`,
`binding_warrant`, and `chapter`. Widening it is small, well-understood work, but the embed
cap in that file needs revisiting once rows carry their full text.

*The renderer is a rewrite, not an extension.* `index.js` today has no concept of chapters,
no expand-in-place interaction, and no contents view. It renders a document list, a reading
pane, and a search result list. Building the topic view described here is closer to writing a
new rendering layer inside the existing app than to adjusting the current one. **This is the
single largest task in the plan** and should be estimated as such rather than as a projection
change.

### Topic page hierarchy (decided, design review pass 1)

Four things compete for the top of a topic page: the title, the scope and excluded-adjacent
line, the tier-composition strip that SC7 requires, and the legacy banner from section 6.
Stacked naively they push chapter 1 below the fold on every visit.

**Decision: the composition strip is adaptive.** One quiet metadata line by default. It
expands to the full strip automatically when the run declined a coverage tier, when a tier
came back empty, or when the topic is legacy and unchaptered. A complete run gets out of the
way; an incomplete one cannot hide.

This applies the design's own progressive-disclosure rule to page chrome rather than only to
content, so there is one interaction model rather than two. It also satisfies SC7 without
making every return visit start with statistics the reader has already seen.

Still unspecified and flagged rather than decided: what the **library landing page** shows
before a topic is chosen, and what a **search results list** looks like before a hit is
clicked. Both are screens with no specification anywhere in this document.

### Interaction states (decided, design review pass 2)

The plan previously specified none of these. Ten exist in the real data.

| State | What the reader sees |
|---|---|
| Source verified | `source checked`, with the domain and the date it was confirmed |
| Source named, never opened | `not opened`, plus a line saying nobody confirmed the page says this |
| Source dead (404) | `dead link`, the date it was last checked, the date the claim *was* confirmed, and that the row is kept rather than deleted |
| Source bot-walled (403) | `could not open`, distinguished from dead: the page probably exists and a human can read it |
| **Library empty (first run ever)** | See decision below |
| Topic has no chapters (legacy) | Flat list under a banner naming the run date and offering the restructure path |
| Chapter with one member | Renders normally. The build gate already prevents a topic of one-member chapters |
| Search with no hits | Names what was searched (all topics, all rows) and offers to clear filters |
| Item with no quote (authored rows, drills) | `authored`, and the absence of a quote is stated rather than shown as a blank |
| Practicum absent for a chapter | Says none was authored, not an empty panel |
| Run failed mid-pipeline | Topic renders with what exists and states which stage did not complete |
| Topic superseded by a re-run | Older run reachable, marked superseded, with a link to the current one |

**Decision on the empty library.** `build_index.py` currently prints to console and calls
`sys.exit(1)` without writing `index.html` at all, so a brand-new user has no page to open.
That is a hard failure, not a missing nicety.

**The builder always writes the page.** When the store is empty, the page itself explains
what will appear there, what a built topic looks like, and the exact command to run. No
seeded example topic: fabricated rows that look researched would sit badly against a design
whose entire premise is traceable provenance.

This also makes the empty screen carry the onboarding, which is the one screen every new
user is guaranteed to see.

### The viewer is served, not opened as a file (decided, design review pass 3)

**This supersedes the "one self-contained file, no server, opens from `file://`" constraint
that earlier drafts of this document stated three times.** That constraint was inherited
from the v0 prototype and never examined. It is not load-bearing, and it was blocking
something worth more than it.

`life-ledger-view` in this same repo already runs the pattern: `viewer-server.mjs` rebuilds
from the JSONL store, serves locally, opens the browser, holds the session, and shuts itself
down within roughly 12 seconds of the tab closing, so a forgotten tab never leaves a process
running. `/study-read` adopts the same shape.

**What serving unlocks, none of which was possible from `file://`:**

| Capability | Why it was blocked before |
|---|---|
| Read/progress marks | A `file://` page cannot write to disk |
| Manual tags on topics | Same. The library browse design assumed tags and had nowhere to put them |
| Notes on rows | Same. `note` was reserved as a record type it could never actually write |
| All three queryable in DuckDB | Browser-local storage is invisible to the store |

**Shape of the per-reader state.** Append-only event logs joined at read time, not mutable
fields on topic records. `progress.jsonl`, `notes.jsonl`, `tags.jsonl`, one line per event,
keyed to the stable IDs Stage 2 assigns. Rewriting a topic record in place would be the only
thing in the system that overwrites history, against `MSR-1` and against the append-only
discipline everywhere else.

**What it costs, stated plainly:** a command instead of a double-click, and a server
lifecycle that has to shut down cleanly. The standalone single-file build drops to a
secondary **export** path for handing one topic to someone else, which this document had
already decided it was.

- One generator, one stylesheet, one interaction model.
- Durability is unchanged: `rows.jsonl` is the durable artifact and always was. Both
  `guide.html` and `index.html` are already build artifacts by the skill's own
  documentation. This removes one of the two.
- "Never render with the model" holds. Both generators are scripts.

### Visual specification (decided, design review pass 4)

**The normative reference is the working prototype:**
`~/.gstack/projects/chzylee-skill-library/designs/study-topic-view-20260813/prototype-a.html`

It is real HTML, not an image, so it can be opened, clicked, and read as the spec. Build
from it rather than from prose. Without this the document describes behavior and says
nothing about appearance, which means an implementer could satisfy every written
requirement with a card grid and icons in circles.

**The load-bearing rules, so a reader knows which properties are the design and which are
incidental:**

1. **Typography carries structure.** Grouping comes from type scale, weight, and whitespace.
   Never from containers. This is the Chi finding applied to the interface itself: visual
   grouping by appearance rather than by the stated principle is the failure mode.
2. **Hairline rules, not cards.** The single tinted panel marks the boundary between reading
   and practising. If a second panel appears, that rule has been broken.
3. **One accent, reserved for outbound source links.** Never for emphasis, never decoration.
   The accent means *this leaves for a firsthand source*, which is the product's whole point.
4. **Badges never compete with the text they annotate.** Smaller, lower contrast, and only
   one axis on the scannable row — `when it matters`. `kind` lives in the expanded detail.
5. **Chapter titles must carry the topic alone.** If you cannot understand the shape of the
   subject by reading only the chapter titles, the chaptering failed, not the styling.
6. **Every disclosure is a native `<details>`.** Keyboard and screen-reader behavior come
   free; a JS reimplementation loses both.
7. **Contrast floor 4.5:1** on all text including metadata, badges, and placeholders. The
   first prototype failed this at roughly 3.3:1 on exactly those elements.
8. **Banned outright:** card grids, icons in circles, centered layouts, decorative shadows,
   rounded corners above 4px on anything that is not a pill, and any ordering by subject.

**How this evolves:** `/impeccable` is the tool for improving the interface. It carries the
anti-slop rules, the product-register conventions, and the contrast and accessibility checks
that produced this list. Run it against the prototype rather than hand-editing toward taste,
and re-run it whenever the visual direction shifts.

### Shared tokens (decided, design review pass 5)

`shared/tokens.css` in the repo. Colors, type stacks, and geometry lifted verbatim from
`study/references/guide.css`, `study-read/references/index.css`, and
`life-ledger/scripts/build_viewer.py`, which had all independently converged on the same
values. Build scripts **inline** it; never link it, which would break the
no-external-requests rule every viewer here holds.

This exists because the fourth viewer re-invented the palette from scratch during this
review, including a teal accent where every existing viewer uses warm brown. The system was
real and consistent and lived in three places and was written in none.

Dark mode comes with it. Two of the three existing viewers already had it; the study
viewers now inherit it rather than each deciding again.

### The library browse view (decided, design review pass 7)

Prototype: `designs/study-topic-view-20260813/prototype-library.html`

**A dense list, not a tile grid.** Card grids are banned by the visual rules above, and a
file browser's list view is the more honest reference for what you asked for: it carries the
facets, tags, dates and progress in a single scan, and it sorts.

Each row: topic name, the boundary line, manual tags, reference class, run date, item and
chapter counts, reading progress, and a one-phrase trust summary (`all open`, `1 dead link`,
`2 unopened`). Alphabetical by default with newest / least-finished / largest as alternate
sorts. Facets across the top for reference class, trust, and tags.

Progress and manual tags only became possible when the viewer stopped being a `file://`
page, so this screen is downstream of the serving decision above.

## 9. Research That Shaped This

Findings from an independent literature scan this session. Sources cited because the design
rests on them.

- **Organization is what makes material expert-grade, not volume.** Chi, Feltovich &
  Glaser (1981): novices sort problems by surface features, experts by deep structure.
  Replicated within the original paper.
  <https://matt.colorado.edu/teaching/highcog/readings/cfg81.pdf>
  → Chapters must be bound by a governing principle. Grouping by surface topic trains the
  novice structure. This is also why the v0's alphabetical sort is actively harmful rather
  than merely unhelpful.

- **A taxonomy is not a sequence.** Bloom's hierarchy has no empirical support as a strict
  cumulative sequence, and treating it as an order is a named, widespread misuse.
  <https://www.edweek.org/teaching-learning/opinion-a-taxonomy-is-not-a-sequence/2003/10>
  · <https://pmc.ncbi.nlm.nih.gov/articles/PMC9727608/>
  → `depth` was classifying *and* sorting. Split them.

- **Mastery is assessment plus correction, not exposure.** Bloom (1968) defines mastery
  learning as formative assessment → correctives → re-test.
  <https://www.uky.edu/~gmswan3/EDC608/Bloom_1968.pdf>
  → "Read everything and reach mastery" does not hold. Practicum is load-bearing, not a
  garnish, which is why it becomes its own record type.

- **Tier disagreement is normal, not a discipline failure.** Webb's Depth of Knowledge has
  weak inter-rater reliability at its middle boundary even with trained human raters.
  <https://www.structural-learning.com/post/webbs-depth-of-knowledge>
  → Anchor every tier to an observable signal in the source text. And accept residual
  variance, because transparency is the guard.

- **Contestedness is a property of a domain, not of an item.** Spiro's ill-structured
  domains. <https://www.ideals.illinois.edu/items/18096/bitstreams/64760/data.pdf>
  → A per-row `contested` tier was proposed during this session and dropped. It lives at
  topic or chapter level.

- **Threshold concepts are out of reach.** Meyer & Land's gateway concepts are diagnosed by
  observing where learners get stuck, not by inspecting sources.
  <https://www.ee.ucl.ac.uk/mflanaga/ISL04-pp53-64-Land-et-al.pdf>
  → Do not spend a version trying to find them from a corpus.

- **The failure-signature framing appears to be original.** The researcher searched for it
  in the education and expertise literature and found nothing equivalent. Cuts both ways:
  no external validation exists for it either.

### Inherited from the author's own Analysis Patterns

`CMP-2` uniform schema across agents · `CMP-3` stable IDs assigned once at synthesis ·
`CMP-4` lineage per row, "the instrument, not bookkeeping" · `CMP-6` blind parallel stages
· `DFN-3` every kill logs its reason · `DFN-10` state what you see in the same turn you
name the source · `DUR-4` pass the spec by path · `DUR-5` stages read upstream output from
disk · `MSR-1` grade, never delete · `MSR-6` the checker is never the producer · `MSR-7`
orchestrator telemetry · `MSR-9` brief the checker to look for absence, already inherited
and already the source of v0.1's best finding · `MSR-12` coverage gates count kinds.

**Deliberately not inherited:** `KD-7` (strip stable IDs from reader-facing output). Here
the ID is how a reader traces a claim back, which is the entire principle. A pattern from
the parent standard that stops applying in this child.

**Open against the standard:** `MSR-6` requires the retro come from a cold reader who
touched no prior stage. The v0's retro is written by the orchestrator, the one agent that
saw everything.

## 10. Approaches Considered

The design above is settled. What is not settled is how to get there from a working v0 with
238 rows in the store.

### Approach A: Amend in place

Change the existing spec, `render.py`, and `build_index.py` incrementally.

- **Effort:** M · **Risk:** Med
- Keeps one working system at all times; each change is small and reversible.
- The schema change touches every stage at once, so "incremental" is partly an illusion.
- `render.py` is being deleted, not amended, so a third of this work is demolition anyway.

### Approach B: Additive pipeline, replaced display

Two halves with different risk, and calling the whole thing "low risk" would be wrong.

- **The pipeline half is genuinely additive.** New schema, new structure stage, new briefs,
  written as new files. The v0 pipeline keeps running untouched until the new one beats it.
- **The display half is not additive. It is a replacement.** `render.py` is deleted, the
  iframe goes, and `build_index.py`'s normalizer and `index.js` are rewritten to carry and
  draw full rows. There is no way to reach the target display without invasive work on the
  one app that exists.

- **Effort:** M/L · **Risk:** pipeline **Low**, display **Med**
- The 238 rows are never at risk. They are data, and the schema change is additive at the
  row level, with `normalize()` already built to absorb versions.
- Gives a real side-by-side on one topic, which is how v0.2 and v0.3 were decided.
  Consistent with how this project already settles this kind of question.
- Mitigation for the display half: the current `index.html` is a build artifact regenerated
  from data by a script under version control, so a bad rewrite is reverted with `git
  checkout` and a rebuild, not repaired.
- Two pipeline paths exist for a while. Only one display does.

### Approach C: Rewrite

Start the skill fresh against the new design.

- **Effort:** L · **Risk:** High
- Cleanest result, no legacy.
- Throws away things the v0 demonstrably got right: pass-the-spec-by-path produced zero
  schema violations across 105 rows, the audit's absence brief produced the best finding of
  any run, the store layout works.
- No working system while it is in progress.

## 11. Recommended Approach

**B — build alongside, cut over on evidence.**

The deciding argument is that this project already knows how to make this kind of decision.
v0.2 versus v0.3 was settled by running the same topic through both arms and comparing
tokens, wall time, and defect catch rate. That comparison is the reason v0.3 was correctly
rejected despite a plausible proposal. The same instrument applies here, and the two named
failure modes are exactly what it would measure: is the output better organized, and did it
cost more.

It is also the only approach where the 238 existing rows are structurally safe rather than
carefully protected.

### Step 1 is a validation, and it has to be a real one

The design names chaptering as its load-bearing bet, so validating it with one agent on one
topic judged by one person would be too thin to trust. It would also contradict `MSR-6`,
which this document invokes elsewhere: the checker is never the producer. And the document's
own cited evidence cuts against a casual test, since Webb's DOK shows trained human raters
diverging on a much easier four-way call.

**The validation:**

- **Input:** existing rows from **three to five completed runs of different reference
  classes** (a tool, a protocol, a body of theory). No new search. Legacy rows already on
  disk, so this costs harvesting nothing.
- **Producer:** one structure agent per topic, chaptering that topic's rows.
- **Checker:** a **separate** agent that never saw the producer's reasoning, scoring each
  chapter against the `because` rubric in section 6: *does it name a mechanism, constraint,
  or shared cause not fully visible in any single member row?*
- **Scored per chapter**, not per topic, as principle / restatement / surface grouping.
- **Every failing chapter is also scored for cause**, attributable to the method or to the
  input. This matters because the legacy rows were produced by the process whose output was
  called "pretty poorly done," so a bad `because` may reflect thin or duplicate-laden source
  rows rather than bad chaptering. Without this the experiment cannot tell a corpus problem
  from a method problem, and would likely blame the method.
- **You read the winners and the losers**, because a rubric an agent applies to itself is
  not evidence, and taste is the thing being tested.

**Blind controls, without which this experiment cannot fail** *(added by the outside voice
in eng review; this was a real hole)*. The checker only ever sees a finished chapter: the
`because` text and the member list. It never sees how the grouping was reached. An agent
asked to write a `because` will produce principle-sounding language whether the grouping came
from causal reasoning or from keyword co-occurrence with a story attached afterward. With
nothing in the scored set designed to score badly, a checker that rubber-stamps everything
returns 100% and the run teaches nothing.

So the scored set includes **deliberately bad chapters, unlabeled and mixed in**:

| Control | Construction | Must score |
|---|---|---|
| Surface grouping | Members grouped by shared keyword in `subject`, with a fluent `because` written over the top | restatement or surface |
| Shuffled members | A real chapter's `because` kept, its members replaced at random from the same topic | restatement or surface |

**If the checker rates a control as principle, the checker is broken and the run is void.**
Re-run the checker; do not read the scores.

**Pass condition, stated before the test rather than after:** the controls all score as
restatement or surface; then at least **70% of real chapters** across all topics score as
principle, **no single topic** falls below 50%, and failures attributed to the method do not
exceed failures attributed to the input. A single topic failing badly means the method works
only where a subject already has obvious structure, which is where it is least needed.

The controls are also what give 70 and 50 a baseline. Without them those are invented
numbers.

**Known limit, recorded rather than fixed:** this runs the structure stage against legacy
rows carrying the old `depth` field. Slice 2 will feed the same stage `kind`, `binding`, and
`choice`-promotion that the validation never exercises, so the go/no-go gate measures a
pipeline slightly different from the one that ships. Accepted, because the alternative is
gating slice 1 on slice 2's schema, which is the coupling the three-slice split exists to
remove.

**If it fails**, the fallback is not "try harder prompting." It is that chaptering becomes a
human-assisted step: the agent proposes, you accept or rename. Slower, still better than a
flat list, and honest about where the judgment actually lives.

### Three slices, not one change (decided, eng review step 0)

The eng review's complexity check triggered on both axes: 10 files, 3 new stages, 6 new
record types, roughly 1,850 lines rewritten or deleted. The finding was that **three
independent changes are bundled here, and only one of them fixes the stated defect.**

Chaptering does not depend on the two-axis schema (grouping works fine against the existing
`depth` field), and neither depends on serving the viewer, which is about storage rather than
organization.

| Slice | Contains | Fixes |

| **1 · Chapters** | `chapter` record, structure stage, renderer rewrite, build gates. Delete `render.py` and `guide.css`. ~6 files. | "40 unorganized rows is a defect." The actual complaint. |

## 12b. Engineering review decisions

**Standing instruction from the author:** the current design is the desired state. Prior
implementation may be overwritten rather than preserved. `render.py`, `guide.css`,
`analysis-topic-knowledge-v0.3.md`, and `v0.3-efficiency-proposal.md` are superseded, not
assets to migrate. The v0.3 comparison's *findings* survive in section 12; the v0.3 spec
files themselves do not need to.

**Gate failures are scoped to the topic, not the build.** `build_index.py` renders every
topic into one page, so failing the whole build on one degenerate `because` would lock the
reader out of every other topic. A failing topic renders flat under a banner naming what
failed; the build succeeds. This reuses the degraded-render path the legacy-topic banner
already needs, so it is one mechanism rather than two.

**The gates get tests; nothing else does yet.** One stdlib-only file, fixture rows covering
each gate's pass and fail case, run with `python3`. No framework, no manifest, no dependency
added to a repo that deliberately has none. The gates are the only mechanized guard the
design claims, and an untested gate that silently stops gating is worse than no gate because
the plan then advertises protection it does not have.

The fixtures double as the worked examples of a genuine versus degenerate `because`, which
section 6 currently describes only in prose.

**`build_index.py:84-86` drops unreadable files silently** and must not:

```python
        try:
            raw = open(path, encoding="utf-8").read()
        except Exception:
            return
```

This contradicts hard rule 7, *"No silent caps. If a stage samples, truncates, or skips, it
says what it skipped."* The same file already handles the `EMBED_CAP` path correctly by
collecting `linked_only` and naming those documents. Unreadable files join that disclosure.

**Recorded without a decision:**

- Chapters have no ongoing audit. The independent chapter checker exists only in the slice-1
  validation experiment; after that ships, chapter quality has no steady-state check, which
  contradicts `MSR-6`.
- `viewer-server.mjs` needs `--port` plus busy-port retry so two viewers can run at once.
- "Run in a fresh session" guards the cost failure mode that measured 58% of v0.1's spend,
  and it is a rule with no mechanism behind it.
- `normalize()` will carry four schema branches and wants a version-dispatch table.
- **`EMBED_CAP = 2_000_000` was sized for truncated rows.** Slice 1 widens the projection to
  full text, so roughly 40 topics of row data alone approaches the cap before any markdown.
  Slice 3 dissolves this: a server fetches a topic on demand instead of baking all of them
  into one file. The architecture change has a performance payoff the plan never claimed.

## 14. Success Criteria

1. **The organization test.** Scored by the independent-checker protocol in section 11: a
   clear majority of chapters rated principle rather than restatement or surface grouping,
   with no topic failing outright. This is the one that decides whether the design worked.
2. **The cold-reader test.** Someone who has not seen the topic can say what it is about
   from the contents view alone. Tested by asking one, not by assertion.
3. **No wall.** No view presents more than **12 items** without structure above them.
   Enforced by the chapter-size gate in section 3, so this is checkable at build time rather
   than by eye.
4. **Every path bottoms out at a source.** Every live row has an `origin` and a resolvable
   link, or an `evidence: authored` marking that says why it does not. Checkable by script.
5. **Cost is reported per stage after every run**, using the same measurement the v0.2/v0.3
   comparison used. **Prediction before the run is deferred**, because it depends on the
   coverage stopping rule in Open Question 3, which is unspecified. Reporting is testable
   now; prediction becomes testable once that rule exists.
6. **The 238 existing rows still render**, per the definition in section 6: queryable and
   readable in a labeled unchaptered view, with `kind: unclassified` and no chapters. Not:
   retrofitted.
7. **A facts-only run announces itself as one**, rather than looking like a complete picture
   that happens to be thin. The artifact states its own tier composition and names what was
   declined.

8. **Every presentation decision traces to evidence about what actually teaches, or is
   marked as craft.** *(Added 2026-08-15, after this document was approved. Recorded as an
   amendment rather than folded in silently.)*

   The bar for this product is **that the reader learns**, and criteria 1 through 7 measure
   organization, structure size, traceability and cost. None of them measures learning. That
   gap was recorded twice and closed neither time, because measuring it directly needs
   learners, a control and a post-test — which this project does not have and is not going
   to build. A criterion nobody can run is not a criterion.

   So the claim moves one level down, to where it can be checked. This document's governing
   principle is **no claim should be made without a traceable cause**, written for claims
   about the world: every row traces to a source. Criterion 8 extends the identical
   discipline to claims about **presentation**: every decision about how material is put on
   the page names the finding behind it, or says plainly that it is craft judgment.

   **Checkable by audit, not by assertion.** Open
   [`design/EVIDENCE-presentation.md`](design/EVIDENCE-presentation.md), take any decision
   visible on the page, and ask two questions: is it in the table, and does the cited finding
   actually say what the decision claims? A decision that is in neither the evidence table
   nor the craft table fails this criterion.

   **What this criterion does not claim, stated so nobody reads more into it.** It does not
   say the artifact teaches. Nothing in the evidence file was measured on this artifact —
   every finding is about resources that demonstrably teach, or about how comparable
   artifacts fail, and that the same moves work here is an inference. The evidence file also
   carries the case *against* its own approach, including a result suggesting that a
   synthesis suppresses source-opening even when the source is one click away, which if it
   holds is a problem for this design rather than support for it.

   The honest summary of criterion 8 is therefore: **the presentation is data-informed and
   the data is on the table where it can be argued with.** That is less than proof of
   learning and considerably more than taste.
